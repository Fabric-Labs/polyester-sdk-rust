# Polyester Rust SDK

Official Rust SDK for Polyester APIs, built for trading bots, backend services,
and automation. Parity with `polyester-sdk-go` and `polyester-sdk-python`, built
on [Connect for Rust](https://github.com/connectrpc/connect-rust) (Buffa + Connect
**0.8.x**) and the checked-in `src/gen/` protobuf bundle.

**Status:** `0.20.1` (git tag `v0.20.1`). Pre-1.0: minor releases may break the API.
The Go, Python and Rust SDKs are released together. Their versions match unless a
change breaks only one SDK's API: Rust 0.20.1 is the release of Go 0.22.1 and Python 0.21.1.
Proprietary license (not open source). API-key only; no browser login or JWT flows.

**MSRV:** Rust 1.90+

`client.address_book` now wraps create/update/delete/copy for entries and tags.
Create and update accept atomic `new_tags`: new tags are created and attached in
the same protected request. When `tag_ids` is also selected on update, the
result is those ids plus the new tags; otherwise currently attached tags are
preserved and `new_tags` are appended. `AddressBookViewInvalidation` includes
`view_revision`. `get_view` is a proto pass-through (`ApiData.raw`); set
`minimum_view_revision` on the request. Regenerated raw views include
`view_revision`. Twitter social-verification `start` forwards the handle as-is,
including an optional leading `@`.

Rows marked **Yes** mean that an SDK wrapper exists; deployment authorization
still applies. Each account read an API key makes needs its own permission on
the key's API-key policy: `READ_API_KEYS` for `api_keys.list` and
`api_keys.get`, `READ_VIP_STATUS` for `vip.get_vip_status`,
`READ_SOCIAL_VERIFICATION` for `social_verification.get` (link status only),
`READ_WITHDRAW_VALIDATION` for `withdraw.validate_destination`,
`READ_DEPOSIT_ADDRESSES` for `deposit.list_addresses`, `CREATE_DEPOSIT_ADDRESS`
for `deposit.create_address`, `READ_SUBACCOUNTS` for `sub_accounts.list` and
`sub_accounts.get`, `READ_SUBACCOUNT_ACTIVITY` for
`sub_accounts.list_activity`, `READ_SUBACCOUNT_MEMBERS` for
`sub_accounts.list_members` (and the members of `sub_accounts.get`),
`READ_SUBACCOUNT_INVITES` for `sub_accounts.list_invites` (and the invites of
`sub_accounts.get`, which leaves out an expansion the key may not read rather
than failing), `READ_GUARD_SIGNER_STATUS` for `guard_signer.get_status`, and
`READ_BALANCES` for `withdraw.get_wallet_balances`. A key scoped to the main
account also needs `READ_ADDRESS_BOOK` (or `MANAGE_ADDRESS_BOOK`) for the main
account's address-book reads, as a sub-account's book already did. VIP status
and social verification need a key scoped to the main account. A key scoped to
a sub-account reaches only that sub-account, and `guard_signer.get_status`
refuses a key for a sub-account another main account owns, even a shared one.
A key without the permission is refused with `permission_denied` and
`AUTH_API_KEY_ACCESS_DENIED` (the withdraw service answers
`ERROR_CODE_PERMISSION_DENIED`; the address book `AUTH_SUBACCOUNT_ACCESS_DENIED`),
and the message names the missing permission. A client that rewrites a
policy's whole action list must keep the permissions it read back. Starting,
confirming and unlinking a social verification (Telegram included) stay
session-only.
Private streams require an Account ID and the corresponding API-key permission.
A successful Centrifugo subscribe call means the token exchange and realtime
handshake completed. The connection and subscription tokens are renewed on the
same connection before they expire; a renewal the API or the server refuses is
reported through the error callback, and the subscription then resubscribes
when the server ends it. The order stream (`orders.subscribe`) returns at once and
reports its handshake through `Connected` and `Error` events. Treat a
structured permission denial as non-transient and update the API-key policy
before retrying.

## Install

crates.io: https://crates.io/crates/polyester-sdk

```toml
[dependencies]
polyester-sdk = "0.20.1"
```

Realtime (Centrifugo) and on-chain Funding helpers are always included. The optional
`realtime` / `chain` Cargo features are empty compatibility flags.

To pin a git tag instead of crates.io:

```toml
[dependencies]
polyester-sdk = { git = "https://github.com/Fabric-Labs/polyester-sdk-rust", tag = "v0.20.1" }
```

For development from a git checkout:

```bash
git clone https://github.com/Fabric-Labs/polyester-sdk-rust.git
cd polyester-sdk-rust
cargo test --lib
```

Pin the Connect runtime: this crate depends on `connectrpc` / `buffa` **0.8.x**.
Review upstream notes before upgrading.

## Quick start

Create an API key in the Polyester app (**API** in the sidebar). Copy the key id
and private key when shown. The private key is only displayed once.
Open the key's **Permissions**, enable **Spot trading**, select the markets it
may trade, and set a maximum order size appropriate for the strategy.

For a subaccount-scoped key, attach an **API key policy** that grants ledger
reads for balance requests and private balance streams. Add the appropriate
trading permissions for create, cancel, modify, and other order mutations.
This API key policy is separate from the **subaccount policy**: the subaccount
policy constrains the subaccount, but does not grant permissions to the key.

```rust,no_run
use polyester::{Client, Config, Result};
use polyester::services::ListMarketOverviewOptions;

#[tokio::main]
async fn main() -> Result<()> {
    let client = Client::new(Config {
        environment: Some(polyester::POLYESTER_DEVNET_ENVIRONMENT.clone()),
        api_key_id: Some("ak_...".into()),
        api_private_key: Some("...".into()), // 64-char hex from key creation
        default_account_id: Some("YOUR_ACCOUNT_ID".into()), // Profile → Account ID
        ..Default::default()
    })?;

    let overview = client
        .market_overview
        .list(ListMarketOverviewOptions {
            limit: Some(5),
            ..Default::default()
        })
        .await?;
    for market in overview.markets {
        let last = market.last_price.as_ref().map(|p| p.as_ticks());
        let index = market.index_price.as_ref().map(|p| p.as_ticks());
        println!("{} {:?} {:?}", market.symbol, last, index);
    }

    let open_orders = client.orders.list_open(None).await?;
    println!("{} open orders", open_orders.orders.len());
    Ok(())
}
```

## Credentials

| Value | Where to find it | Config field |
| --- | --- | --- |
| API key id | **API** → create or view key | `api_key_id` |
| API private key | Shown once when the key is created | `api_private_key` |
| Account ID | **Profile** → **Account ID** | `default_account_id` |

Pass `Config.environment` so API, websocket, RPC, and contract pins stay
together. `POLYESTER_DEVNET_ENVIRONMENT` is the `Client::new` default.
`POLYESTER_TESTNET_ENVIRONMENT` targets public testnet
(`api.testnet.polyester.com`, chain `888169`). Custom / VPC endpoints use
`create_polyester_environment` or `environment.with_urls(...)`. `api_url` /
`ws_url` remain as transport overrides.

Pass credentials on `Config` / `Client::new`. The SDK does not implicitly read
environment variables unless you call `Client::from_env`. `from_env` also reads
`POLYESTER_ENV=devnet|testnet`.

`api_private_key` accepts the 64-character hex Ed25519 secret from key creation.

`default_account_id` is the **Account ID** string from your Profile page. Use the
value exactly as shown in the app. Do not use an internal numeric id.

`default_account_id` is optional for public market-data calls. It is required for
account-scoped operations such as private realtime channels, bucket transfers, and
some ledger writes.

Automatic request signing gives concurrent identical calls distinct authentication tuples. Cloned
and independently constructed credentials with the same key id share a process-wide allocator.
The signing protocol has no cross-process nonce, so assign one API key per process; sharing a key
between processes can produce identical authentication tuples. Timestamps can lead the local clock by at most half a
second; larger async bursts wait through Tokio-aware backpressure instead of blocking executor threads,
reusing a signature, or running past the API's limit, which refuses a timestamp more than one second
ahead of the server clock as `Error::TimestampSkew`. Keep the host clock synchronized. If the bounded
capacity wait is exhausted, the call returns retryable `Error::RateLimit`. Direct low-level
`Credentials::sign_request` calls never sleep; use `sign_request_async` in async applications.

`Config::recv_window_ms` sets the receive window of every signed API request: the server processes
a request only until its signing timestamp plus that many milliseconds, sent as the signed
`X-API-RECV-WINDOW` header. It must be from 1 to 60000, and `Client::new` refuses any other value
with `Error::Validation` before anything is sent. `None`, the default, sends no header, and the
server applies 5000. A request that arrives after its window is the retryable
`Error::TimestampSkew`; one that waited past it before admission is an `Error::Api` with code
`order_codes::REQUEST_DEADLINE_EXCEEDED`, also retryable. Both changed nothing, and a retry signs
again with a fresh timestamp. Realtime token requests always use the default window. To sign
requests yourself, `Credentials::sign_request_with_recv_window` (and its async variant) and
`auth::canonical_signing_string_with_recv_window` put the window's line right after the timestamp
line.

## Authentication patterns

**Recommended: explicit config**

```rust,no_run
use polyester::{Client, Config};

let client = Client::new(Config {
    api_key_id: Some("ak_...".into()),
    api_private_key: Some("...".into()),
    default_account_id: Some("YOUR_ACCOUNT_ID".into()),
    ..Default::default()
})?;
```

**If your deployment stores secrets in environment variables**, read them in your
application and pass them to `Client::new`:

```rust,no_run
use std::env;
use polyester::{Client, Config};

let client = Client::new(Config {
    api_key_id: env::var("POLYESTER_API_KEY_ID").ok(),
    api_private_key: env::var("POLYESTER_API_PRIVATE_KEY").ok(),
    default_account_id: env::var("POLYESTER_ACCOUNT_ID").ok(),
    ..Default::default()
})?;
```

`Client::new` never implicitly reads the process environment.

**Scripts and local tests only:** `Client::from_env()` loads
`POLYESTER_API_KEY_ID`, `POLYESTER_API_PRIVATE_KEY`, and optionally
`POLYESTER_ACCOUNT_ID` / `POLYESTER_API_URL` / `POLYESTER_WS_URL`. This is a
convenience helper, not the primary integration pattern.

```rust,no_run
let client = polyester::Client::from_env()?;
```

`api_url` / `POLYESTER_API_URL` must be an HTTP(S) base URL without a query
string or fragment. `ws_url` / `POLYESTER_WS_URL` must be `wss://` or `ws://`.
Remote plaintext (`http://` / `ws://` to a non-loopback host) is rejected
unless `Config::allow_insecure_http` is set, or `from_env` sees
`POLYESTER_ALLOW_INSECURE_HTTP=1`. Loopback plaintext stays allowed for local
tests.

## Catalog readiness

`Config::hydrate_catalogs` defaults to `true`. When constructed inside a Tokio
runtime, the client starts loading two catalogs in the background, each on its
own: the **spot config** (`marketdata.v1.MarketDataService/GetSpotConfig`:
pairs, symbol IDs, scales), which every spot trading call needs, and the
**funding config** (`chain.zipper.v1.ZipperService/GetDepositWithdrawConfig`:
deposit and withdrawal assets and chains).
Every method that names a market by symbol, or needs a pair's catalog scales,
waits for the spot config itself, so it can be called right after the client is
created. When that load failed, such a method returns `Error::CatalogHydration`,
which holds the failure; a symbol the hydrated catalogs don't know returns the
`Error::Validation` "unknown symbol". `zipper.subscribe_zipped_asset_supply`
waits for the funding config the same way, and spot calls never wait for, or
fail with, the funding config.

`wait_for_catalogs()` reports **spot readiness**: it returns `Ok` once the spot
config has loaded and validated, without waiting for the funding config.
`wait_for_funding_catalog()` reports the funding config; read the zipper
catalog and `catalogs.ledger_id_for_asset` after it returns `Ok`. Each returns
`Error::CatalogLoad` when its catalog could not be loaded, and loads it again
on the next call.

Only what reads the funding config waits for it: the zipper supply stream,
which decodes with its scales. A waiting call sends nothing until the config
loads, and returns `Error::CatalogHydration` naming the funding config,
without sending, when it failed. Deposit addresses and withdrawals
(`deposit.list_addresses`, `deposit.create_address`, `withdraw.create_*`) and
`zipper.get_deposit_withdraw_config` read nothing from it and work while it is
loading or failed. `catalogs.ledger_id_for_asset` doesn't wait: `None` means
either that the funding config has not loaded (yet, or its load failed) or
that it does not know the asset, so await `wait_for_funding_catalog()` first.
With `hydrate_catalogs: false` nothing loads and nothing waits, as before.

These two reads change nothing, so a read that times out or loses its
connection (`client error (SendRequest)`) is read again: at most 3 reads per
catalog, 250ms and then 500ms apart, each retry on a connection pool of its
own, all within `Config::catalog_timeout` of `Client::new` (default twice
`Config::timeout`). A read that keeps stalling fails within that deadline. Any
other error answer, and a catalog that does not validate, fails at once. No
other call is retried this way, and mutations never are.

`Error::CatalogLoad` holds a `CatalogLoadFailure` that names the catalog
(`catalog`: `"spot"` or `"funding"`), the `operation`, the kind of failure
(`failure`: `"timeout"`, `"connection_closed"`, `"connect_failed"`,
`"unavailable"`, `"invalid"` or `"error"`), the number of reads (`attempts`),
`elapsed`, and the edge's reference of the last failed response
(`response_ref`, the `cf-ray` header) when one arrived; `source` is the last
failure, also returned by `std::error::Error::source`. Its message drops URL
credentials. No SDK error prints a credential anywhere in its chain: every
error mapped from a Connect call is redacted where it is mapped, so each URL an
answer or a transport quotes loses its userinfo, query and fragment, and a
proxy URL from the environment reads `[proxy]`, in `Display`, `Debug` and every
`source()`, problem details and a rate limit's `detail` included. A URL that
does not parse is dropped whole. The client's own secrets read `[REDACTED]`
however an answer quotes them: the userinfo and password of its `api_url` and
`ws_url` and of a proxy the environment sets (raw and percent-decoded), and
its API private key. Limitations: a password shorter than 4 characters is not
replaced where it stands alone, since replacing so short a string would
mangle ordinary text; and a request signature is not redacted when the server
echoes it back, since it is single-use and expires with its receive window. A `CatalogLoadFailure` message reads, for example, `catalog hydration failed: funding config
(chain.zipper.v1.ZipperService/GetDepositWithdrawConfig) connection closed
after 3 attempts in 0.8s: ...`.

Timeouts, from the outside in: `Config::catalog_timeout` bounds the startup
reads of each catalog, retries included; `Config::timeout` (default 10s) is
each request's deadline, enforced locally and sent as `Connect-Timeout-Ms`;
the HTTP client allows 5s for the TCP connect and 20s to establish a
connection (DNS, TCP and TLS), negotiates HTTP/2 or HTTP/1.1 by ALPN, and has
no read timeout of its own. This SDK does not use HTTP proxies:
`HTTPS_PROXY` and the like are ignored. Methods that only label their results from
the catalogs, such as `market_overview.subscribe` and `fees.get_spot_fee_rates`,
wait too and leave the labels empty when hydration failed. With
`hydrate_catalogs: false` nothing waits. Await readiness yourself to learn early
whether hydration failed, or to hydrate again after a failure:

```rust,no_run
let client = polyester::Client::from_env()?;
client.wait_for_catalogs().await?;
```

The hydrated zipper config also seeds each variant's supply, read with
`catalogs.supply_for_zipped_asset_id`; `zipper.subscribe_zipped_asset_supply(true)`
keeps it current.

Catalogs supply scales and symbol IDs for encoding. Tick/step/minimum
quantity and notional checks are venue-owned (preview/admission); the SDK does
not preflight those pair constraints client-side.

Public methods may still accept display `symbol` strings. Connect is
`symbol_id`-only except `GetSpotConfig` (which still returns both `symbol`
and `symbol_id`). The SDK trims display symbols, resolves them through the
hydrated catalog, and fails closed on unknown values. It does not forward raw
symbol strings onto Connect fields that no longer exist. A read that takes
both a `symbol` and a `symbol_id` (`market_data.get_trades_with`,
`get_candles_with`, `orders.list_history_with`) refuses a name and an ID for
different markets with `Error::Validation` before sending. Optional ListOpen
limits reject an explicit `Some(0)`; other zero-means-default proto limits
pass `0` through as the server default.

If a client is constructed before entering a Tokio runtime,
`wait_for_catalogs()` starts hydration on the current runtime. Scaled bot inputs
must carry their source scale. `AssetAmount::from_scaled(..., None, ...)` is
accepted for composition only and fails closed on transfer/withdraw encoding
unless the request's `amount_scale` / `quantity_scale` is explicit. Prefer
`from_decimal_str` / `from_decimal`, or pass `Some(scale)` to `from_scaled`.

Successful private subscriptions are returned only after token exchange,
websocket connection, and channel subscription complete. Missing credentials
fail immediately with `Error::Auth`. Response `*_ts_ns` fields are forwarded as
received (including millisecond-shaped values if a producer emits them).

## Create and cancel orders

```rust,no_run
use polyester::models::{CreateOrderType, CreateSide, CreateTimeInForce};
use polyester::services::OrdersService;
use polyester::types::{Price, Quantity};

client.wait_for_catalogs().await?;

let mut params = OrdersService::create_params(
    "BTC-USDT",
    CreateSide::Buy,
    CreateOrderType::Limit,
    Quantity::from_decimal_str("0.01", 8, None, None)?,
    Some(Price::from_decimal_str("100", None)?),
    Some("my-bot-001"), // recommended whenever you may retry
);
params.time_in_force = Some(CreateTimeInForce::Gtc);
params.post_only = Some(true);

let result = client.orders.create(params).await?;
println!("{} {}", result.status, result.order_id);

client
    .orders
    .cancel_by_client_order_id("my-bot-001", Some("BTC-USDT"), None)
    .await?;
```

`client_order_id` is **optional** (matches the API). Pass `None` for one-shot
creates. **Set a stable non-empty value when you may need to reconcile** after
an ambiguous transport/server failure. Without it you cannot tell whether the
first attempt admitted the order. After an unknown outcome, look up that id
(`get` / `list_open`) before creating again. A second create with the same id
is rejected (`CONFLICT_DUPLICATE_CLIENT_ORDER_ID`) even when the payload
matches. Only create again with that id if reconciliation shows the first
attempt did not admit.
Client order ids accept 1 to 36 ASCII letters, digits, `.`, `_`, `:`, `/`, and
`-`. Batch create accepts at most 20 orders; batch cancel and replace accept at
most 50 items. Treat a cancel response as an
admission acknowledgement and reconcile with `list_open` before releasing local
state. Within one batch, non-empty client order IDs must be unique; omitted and
blank IDs remain allowed.

Create sizing is explicit: set exactly one of base `quantity` or
`max_quote_debit_scaled` (a typed hard all-in quote-debit budget). Construct the
latter with `Quantity::from_quote_decimal_str` / `from_quote_decimal` /
`from_quote_scaled`; the SDK validates its `OrderQuote` domain and scale against
`Catalogs::quote_quantity_scale_for_symbol`.

```rust,no_run
let quote_scale = client
    .catalogs
    .quote_quantity_scale_for_symbol("BTC-USDT")
    .expect("catalog hydrated with quote scale");
params.quantity = None;
params.max_quote_debit_scaled = Some(Quantity::from_quote_decimal_str(
    "25.00",
    quote_scale,
    Some("BTC-USDT".into()),
    client.catalogs.symbol_id_for_symbol("BTC-USDT"),
)?);
```

Use `OrdersService::preview(PreviewOrderParams::new(...))` to check whether an
order intent is currently admissible before submitting. Preview sends the same
`OrderIntent` contract as create (sizing, execution, fee asset, STP, optional
attached risk). The host runs an admissibility check only: no hold is placed,
and `client_order_id` is accepted but not claimed. The result reports
`admissible`, optional typed `rejection` (`OrderErrorDetail`), optional
`resolved_base_qty`, optional `protected_price_bound`, and `evaluated_at_ms`.
Known rejection codes use stable labels such as `BAD_QTY`.
Preview no longer returns fee/quote estimates. Preview is not deployed on every
API host, so handle an unimplemented/not-found response and do not make Preview
a prerequisite for order submission. Fee selection is `FeeAsset::Quote` or, for
BUYs only, `FeeAsset::Base`; the former `received` fee mode no longer exists.

A buy sized by a quote amount (`max_quote_debit_scaled`, market or limit IOC)
can carry `attached_risk` like any other order: the server checks each leg
against the pair's minimums at the quantity the amount buys at the order's
price limit, and the legs then protect what the fills buy.

`CreateOrderParams.self_trade_prevention` (`OrderSelfTradePrevention`,
default `ExpireMaker`) also applies to the order's attached take-profit,
stop-loss and trailing-stop exits, which have no mode of their own. Order
reads report it as `Order.self_trade_prevention_mode` (`expire_taker`,
`expire_maker`, `expire_both`), and each leg's trigger as
`Trigger.self_trade_prevention_mode`. An attached exit never trades with the
order it protects: when it fires while that order still rests, the order's
unfilled rest is canceled first (fills before stand) and the order ends
`canceled` with `CANCEL_REASON_ATTACHED_EXIT_FIRED`.

Standalone trailing stops take either side. A SELL trailing stop tracks the
highest price and fires a market-IOC child; it takes no `limit_price`. A BUY
trailing stop tracks the lowest price and requires `limit_price`: its maximum
price, the most its child pays per unit, fixed at create. Attached
trailing-stop risk takes the side opposite the parent. Trigger reads project
`trigger_type`, `side` and `parent_order_id`. A standalone BUY trailing stop
reads as an IOC limit child (`order_type` `limit`, `time_in_force` `ioc`) with
its maximum price as `limit_price`, and so does an attached BUY leg (the
trailing stop of a SELL order); a SELL one, standalone or the trailing stop of
a BUY order, reads as a market IOC child with any cap in `max_slippage`. The trailing details
carry the trough (BUY) or peak (SELL) price.

An attached trailing stop on a SELL order buys back, so it requires
`TrailingStop.limit_price`: the most its exit pays per unit, at least its
`activation_price` when that is set. An attached trailing stop on a BUY order
sells and takes no `limit_price`. Order creates check both locally with
`Error::Validation`; a modify, which does not carry the order's side, checks
the limit's price rules and leaves the side rule to the server. When the
trailing stop of a SELL order fires, its child is a limit IOC order at
`limit_price` (lower when `max_slippage` caps it below): it fills what it can
at or below the limit, and the rest is canceled instead of resting. The
trailing stop of a BUY order exits with a market child. `orders.get_with`,
`orders.list_open_with` and `orders.list_history_with` with
`include_attached_risk`, and `orders.subscribe` updates, return the limit as
`TrailingStop.limit_price`, `None` when there is none.

`CreateOrderParams`, `PreviewOrderParams`, `CreateTriggerParams`, `RiskLeg` and
`TrailingStop` are `#[non_exhaustive]`, so a new optional field is not a
breaking change. Build them with their constructors and set optional fields
afterwards:

```rust,no_run
use polyester::models::{
    AttachedRisk, CreateOrderParams, CreateOrderType, CreateSide, RiskLeg, TrailingDistance,
    TrailingStop,
};
use polyester::types::{Price, Quantity};

let mut params = CreateOrderParams::new("BTC-USDT", CreateSide::Sell, CreateOrderType::Limit);
params.quantity = Some(Quantity::from_decimal_str("0.01", 8, None, None)?);
params.price = Some(Price::from_decimal_str("100000", None)?);
params.attached_risk = Some(AttachedRisk {
    take_profit: Some(RiskLeg::market(Price::from_decimal_str("95000", None)?)),
    // On a SELL order the trailing stop buys back, so it needs its maximum price.
    trailing_stop: Some(
        TrailingStop::new(TrailingDistance::Bps(100))
            .with_limit_price(Price::from_decimal_str("105000", None)?),
    ),
    ..Default::default()
});
let result = client.orders.create(params).await?;
```

To name the market by its Connect ID instead, such as a `symbol_id` from a
market-data stream, use `CreateOrderParams::for_symbol_id` (or
`PreviewOrderParams::for_symbol_id`), or set `symbol_id` next to `symbol`; both
must then name the same market. The ID must be in the hydrated catalog, which
supplies the pair's scales, and an unknown ID, a zero ID or a contradicting
symbol is refused before sending.

```rust,no_run
use polyester::models::{CreateOrderParams, CreateOrderType, CreateSide};
use polyester::types::{Price, Quantity};

let mut params = CreateOrderParams::for_symbol_id(1, CreateSide::Buy, CreateOrderType::Limit);
params.quantity = Some(Quantity::from_decimal_str("0.01", 8, None, None)?);
params.price = Some(Price::from_decimal_str("90000", None)?);
let result = client.orders.create(params).await?;
```

The SDK checks the trailing stop's maximum before sending and refuses a
mistake with the code, field path and rule ID the server answers, as an
`Error::Api` with one entry in `Error::violations()`
(`order.attached_risk.trailing_stop.limit_price_ticks`): set on a BUY parent,
`ERROR_CODE_BAD_PRICE` / `sell_unset`; missing on a SELL parent,
`ERROR_CODE_TRIGGER_BUY_REQUIRES_LIMIT` / `buy_required`; below the activation
price, `ERROR_CODE_BAD_PRICE` / `buy_at_least_activation`. A modify or batch
replace sends the maximum as given: it does not carry the order's side, so the
server applies the side rule and answers `ERROR_CODE_BAD_PRICE` with no
violation.

Stop-loss, take-profit and trailing-stop triggers, and attached take-profit,
stop-loss and trailing-stop legs, can watch the index price instead of the
last trade price. Set `CreateTriggerParams.trigger_price_source` to `index`
(labels `last`, `index`, `mark`, as trigger reads report them) or a leg's
`trigger_price_source` to `TriggerPriceSourceKind::IndexPrice`; leave it
`None` to watch the last trade price. A market without an index price
rejects an index-price leg or fails an index-price trigger with
`index_price_unavailable`. Mark price is not supported on spot: a `mark`
source or `TriggerPriceSourceKind::MarkPrice` leg fails locally with
`Error::Validation`. Order and trigger reads report the source, so a read leg
can be sent back unchanged.

Stop-loss and take-profit triggers with a market child accept a slippage cap,
`max_slippage_ticks` or `max_slippage_bps` (at most one; a SELL child takes
fewer than 10000 bps). Without one, the pair's default market slippage
applies. A limit child takes no cap; its `limit_price` bounds it. Trigger
reads expose the cap as `Trigger.max_slippage`. A TWAP market child takes the
same cap, applied to each slice; `max_slippage_ticks` is positive wherever a
create sends it. `Trigger.max_slippage` reports the cap of a stop-loss or
take-profit market child, of a trailing stop and of a market TWAP's slices in
the variant it was set in (`MaxSlippage::Ticks` or `MaxSlippage::Bps`), and
`None` when none is set: the pair's default then applies. A trailing stop's
cap also stays in its `TriggerDetails::Trailing` details. No
trigger child has a GTD execution, so `CreateTimeInForce::Gtd` fails locally
with `Error::Validation` for every trigger type. A market child (stop-loss,
take-profit or TWAP) and a trailing stop always execute IOC: leave
`time_in_force` `None` or set `Ioc`; `Gtc` and `Fok` fail locally with
`Error::Validation` instead of being sent as IOC.

Market orders are IOC and enforce a slippage-derived execution boundary: the
contract's only market execution is `market_ioc`. Leave a market order's
`time_in_force` `None` or set `Ioc`; `Gtc`, `Fok` and `Gtd` fail locally with
`Error::Validation` ("tif=fok is only valid for limit orders") before
`create`, `preview` or `batch_create` sends anything. See
[Market Order Price Protection](https://polyester.com/docs/developer-docs/shared-concepts/market-order-price-protection)
before overriding `market_max_slippage`. `MaxSlippage::Bps` is 1–10000 for a
buy and 1–9999 for a sell: a 100% cap would leave a sell no positive price.
An attached trailing stop's `max_slippage` takes at most 9999 bps on either
side.

With the catalogs loaded, order reads (`orders.get`, `list_open`,
`list_history`, `trades.list`, and `orders.subscribe` orders and fills) and
trigger reads (`qty`, a TWAP's or ladder's `executed_qty`) give each quantity
the pair's base quantity scale, so `order.cum_qty.unwrap().format(None)` works
without passing a scale. Reads wait for a spot config load in progress, never
for the funding config; if that load failed, quantities keep no scale and
`format` needs one.

Orders carry exact execution totals. `Order::avg_price()` is the exact average
execution price (from `avg_price_e18`, 18 decimals); `avg_px` stays the same
average rounded down to 1e-9. `Order::cum_quote(base_quantity_scale)` is the
exact quote amount of the fills before fees (from `cum_notional`, in units of
10^-(9 + the pair's `base_quantity_scale`)), and `Order.fee_total` is their
fee net of rebates in `fee_asset` (`amount()`, `is_rebate`, `qty`). All are
`rust_decimal::Decimal`, never floats, and zero with no fills; a value that
needs more digits than a `Decimal` holds reads `None`, never a rounded value.
`cum_quote` is exactly the quote the fills settled when the pair's
`base_quantity_scale` is at most 9; above that it can exceed it by less than
1e-18 per fill, and so can `quote_used`. Order history
reads and `get` with execution history carry `fee_total`; open-order reads and
stream updates leave it `None`. For a buy sized by a quote amount,
`Order::quote_used(base_scale)` is what the fills used (fees in quote added,
a rebate subtracted, a base fee left out) and
`Order::quote_unspent(base_scale, quote_scale)` what is left of
`submitted_max_quote_debit_scaled`. Both are `None` until `fee_total.qty`
equals `cum_qty`: a fill's fee is recorded shortly after the fill. Such a buy
ends `filled` once it spent its amount, and `canceled` with
`CANCEL_REASON_MARKET_REMAINDER` or `CANCEL_REASON_IOC_REMAINDER` when the book
or its price limit stopped it first.

```rust,no_run
let read = client.orders.get(OrderKey::OrderId(order_id), None).await?;
if let Some(order) = read.order {
    let base = client.catalogs.base_quantity_scale_for_symbol_id(order.symbol_id);
    let quote = client.catalogs.quote_quantity_scale_for_symbol_id(order.symbol_id);
    println!("average {:?}", order.avg_price());
    if let (Some(base), Some(quote)) = (base, quote) {
        println!("used {:?}", order.quote_used(base));
        println!("unspent {:?}", order.quote_unspent(base, quote));
    }
}
```

### Waiting for an order's trades

An order shows a fill as soon as it executes; its trades are recorded shortly
after. `orders.wait_for_order_trades_complete(key, timeout)` polls
`orders.get`, every execution page included, until the order has ended
(`status` `filled`, `canceled` or `rejected`) and its trades add up to
`cum_qty`, then returns that read. It reports completion at the same point as
the Go and Python SDKs. `executions_complete` alone is not completion: it is
also true for a working order whose fills so far are all recorded, for example
after a partial fill. A working order keeps the wait polling until it ends or
the timeout passes, which returns `Error::Transport`. To check the trades
recorded so far on an order that is still working, read it with `orders.get`
and compare its trades to `cum_qty`.

```rust,no_run
let detail = client
    .orders
    .wait_for_order_trades_complete(OrderKey::OrderId(order_id), Duration::from_secs(20))
    .await?;
println!("{:?} {} trades", detail.order.map(|o| o.status), detail.trades.len());
```

A replacement order reports `Order.inherited_cum_qty`, the filled quantity it
inherited from its predecessors (zero for an original order); `cum_qty` minus
it is what this generation executed. A duplicate `client_order_id` is
rejected with `ERROR_CODE_CONFLICT_DUPLICATE_CLIENT_ORDER_ID`, and
`Error::existing_order_id()` (or `BatchCreateResultItem.existing_order_id`)
names the order that holds it when the server knows it.

An ended order says why. A `rejected` order carries `Order.reject_reason`,
the order error code the Orders API returns for the same refusal and in the
same form as `Error::Api`'s `code` (for example `ERROR_CODE_POST_ONLY_CROSS`).
A `canceled` order carries `Order.cancel_reason`, a `CancelReason` proto name
such as `CANCEL_REASON_USER_REQUEST`, `CANCEL_REASON_IOC_REMAINDER`,
`CANCEL_REASON_STP_EXPIRE_MAKER`, `CANCEL_REASON_REPLACED` or
`CANCEL_REASON_GTD_EXPIRED`. Both are `None` for every other status. A value
this SDK does not know yet keeps its number: `UNKNOWN_ERROR_CODE(<n>)` and
`UNKNOWN(<n>)`. Match on these codes, not on message text.

Each spot pair publishes order limits, read with
`market_data.get_spot_config()` (`SpotConfig.pair_order_limits`,
`SpotConfig.max_open_orders_total`) or, after hydration,
`catalogs.pair_order_limits_for_symbol("BTC-USDT")` and
`catalogs.max_open_orders_total()`. `max_limit_qty_base`,
`max_market_qty_base`, `max_order_notional_quote` and
`max_market_notional_quote` are decimal strings, `None` when the pair has no
maximum (not zero); an order above one is rejected with `MAX_QTY` or
`MAX_NOTIONAL`. `max_open_orders_per_pair` and `max_open_orders_total` are
the default resting-order limits for a typical account (0 when unpublished);
an account may have a lower limit of its own.

```rust,no_run
client.wait_for_catalogs().await?;
if let Some(limits) = client.catalogs.pair_order_limits_for_symbol("BTC-USDT") {
    println!("max notional {:?}", limits.max_order_notional_quote);
}
```

Use **decimal strings** or `Decimal` for human-facing `qty` / `price` inputs.
Do **not** pass floats. Price ticks are Polyester protocol price units (fixed
1e9: one tick is 0.000000001 quote units), not market tick-size alignment (server validates tick size).

```rust,no_run
let params = OrdersService::create_params(
```

## User trade fees

`trades.list(subaccount_id, limit)` remains. Use
`trades.list_with(ListUserTradesOpts { ... })` for symbol filters, `page_token`,
and `after_match_id`. When `after_match_id` is set, a resolved non-zero
`symbol_id` is required (display `symbol` or numeric id).

`UserTrade` fee fields are fixed **18-decimal** magnitudes of `fee_asset`
(`fee_amount_e18`, `referral_share_amount_e18`), not catalog asset-scaled
integers. Convert e18 → the fee asset's catalog scale before subtracting from a
BUY fill's base quantity.

Magnitudes are unsigned. Treat `fee_amount_e18` as a **debit** unless
`fee_is_rebate` is true (then it is a **credit**). Proto3 omits false, so the
rebate flag is sparse on the wire.

`client.fees.get_spot_fee_rates` returns the account target's current effective maker/taker
percents per listed symbol (optional `symbol_id` filter). That is the live effective-rate
surface, not a guaranteed quote of every future fill. The completed user-trade record still
owns the exact charge.

Rows also expose `reserve_fee_rate_percent`,
`post_only_reserve_fee_rate_percent`, `next_change_at` and `breakdown`. Size a
buy limit order that pays its fee in the quote asset with the reserve rate,
using the post-only reserve rate for a post-only order. A buy sized by a quote
amount reserves at the lower of the reserve and taker rates. Effective
maker/taker rates apply to fills. Refetch rates at
`next_change_at` when present. `breakdown` contains tier rates, a market
multiplier, account discounts and a referral discount. Optional components
and times may be `None`; absent account discounts decode as an empty vector.

See the [contract migration notes](docs/contract-748066a.md) for the full
fee model and exact integer budgeting guidance.

## Product changelog

`client.changelog` reads the product changelog published for the environment
the API host serves. It is public and read-only: it needs no API key, and
requests are rate-limited per client address. Responses are newest post first.

- `list_posts(opts)` returns one page of post summaries with change counts;
  `posts(opts)` is a stream over every page. A published post can be
  republished, for example to correct its copy or withdraw a change: its
  `slug`, `published_at` and change ids stay the same, `revision` (from 1)
  increases and `updated_at` is when the current revision was published. To
  follow edits, read a post again when its `revision` differs from the one you
  hold, and drop a post that is no longer listed.
- `get_post(slug)` returns one post with its sections and changes. A slug is the
  post's coverage cutoff date, `YYYY-MM-DD`; a later post on the same day gets
  `-2`, `-3`. An unknown slug is `Error::Api` with code `NotFound`.
- `list_changes(opts)` returns one page of individual changes across posts,
  filtered by category, surface, audience, `action_required`, first publication
  time (`start_time` inclusive, `end_time` exclusive) or post; `changes(opts)`
  is a stream over every page that yields each change id once: when a post is
  republished during the walk, paging restarts at that post's first change.
  Values within one filter combine with OR.
- `breaking_changes_since(t)` and `action_required_since(t)` collect every
  matching change published at or after `t`, each once with the wording last
  received. They filter on first publication, so they don't report an edit to
  an older post; compare `revision` for that.

Category, audience and surface are lowercase labels (`breaking_change`, `api`,
`market_makers`, `market_data`, `quickswap`, `rewards`, ...; see the
`CHANGELOG_*` constants in `polyester::models`). A value newer than this SDK
reads as `unknown(<n>)`. `ChangelogSection::surface` is the product area a
section covers, empty for a section not tied to one area (such as the changes
that need your attention); `list_changes` takes at most 10 `surfaces`. With
`WireFormat::Json`, an enum name this SDK does not know reads as unset (and is
dropped from a list) instead of failing the call. `ChangelogChange::id` is
the change's public base58 id. The service returns `Unavailable`
(`Error::Server`) while it is starting.

```rust,no_run
use futures_util::TryStreamExt;
use polyester::services::{ListChangelogChangesOptions, ListChangelogPostsOptions};
use std::time::{Duration, UNIX_EPOCH};

let posts: Vec<_> = client
    .changelog
    .posts(ListChangelogPostsOptions::default())
    .try_collect()
    .await?;
let newest = client.changelog.get_post(&posts[0].slug).await?;

let since = UNIX_EPOCH + Duration::from_secs(1_767_225_600); // 2026-01-01
let breaking = client.changelog.breaking_changes_since(since).await?;
let api_changes = client
    .changelog
    .list_changes(ListChangelogChangesOptions {
        surfaces: vec!["api".into()],
        start_time: Some(since),
        ..Default::default()
    })
    .await?;
```

`examples/changelog.rs` runs these calls against devnet.

## Price alerts

Price alerts are available on devnet; they are not yet routed on testnet,
where these calls fail. `client.alerts` creates durable alerts ("tell me when
BTC-USDT falls to 90,000") that the exchange evaluates and delivers in-app
and/or to your linked Telegram account. Alerts belong to the main account:
use an API key scoped to the main account. A key scoped to a sub-account is
refused with `Error::PermissionDenied` and code `SUBACCOUNT_KEY_REFUSED`.

```rust,ignore
use polyester::models::{AlertChannel, AlertDirection, CreateAlertParams, ListAlertsOptions, UpdateAlertParams};
use polyester::types::Price;

let alert = client.alerts.create(
    CreateAlertParams::new(
        "BTC-USDT",
        AlertDirection::Below, // inclusive: fires at a price <= the alert price
        Price::from_decimal_str("90000", None)?,
        vec![AlertChannel::InApp, AlertChannel::Telegram],
    )
    .with_idempotency_key("bot-7:alert-1"), // a retry returns the alert created first
).await?;
// Move the level, keyed so a retry applies at most once.
let moved = client.alerts.update(
    UpdateAlertParams::new(alert.alert_id.clone(), alert.revision)
        .with_price(Price::from_decimal_str("91000", None)?)
        .with_idempotency_key("bot-7:alert-1:move-1"),
).await?;
client.alerts.cancel(&alert.alert_id).await?;
```

An alert watches the market's last traded price or its index price
(`AlertPriceSource`); without one it watches the index price where the market
has one and the last price otherwise, and the returned alert states it. The
market's price at creation is recorded as `reference_price`; an alert whose
condition already holds then starts unarmed and fires only after the price
moves to the other side and crosses back. It fires once: `status`
`"triggered"`, with `triggered_at` and `triggered_price`. A late price or a
stalled feed never fires it. Status values are `"active"`, `"triggered"` and
`"cancelled"` (the contract's spelling).

`update` sends only the fields set on `UpdateAlertParams` with the
`expected_revision` you last read; a stale one is refused with code
`REVISION_CONFLICT`, so read the alert again. An update that sets no field
changes nothing on an active alert and sets a triggered one again as it is.
`outcome` is `"applied"`, `"unchanged"` or `"replayed"` (the idempotency key
was already used for this request; nothing was applied now): tell a retry
from a fresh change by `outcome`, never by `revision`. `list` pages newest
first, up to 200 per page; `all` streams every page. Refusals keep their
contract codes (`polyester::errors::alert_codes`): `PRICE_UNAVAILABLE` changed
nothing and is retryable; `SERVICE_UNAVAILABLE` leaves a create, update or
cancel outcome unknown, so send it again with the same idempotency key
(`cancel` is idempotent) or read the alerts back.

## Server build version

`client.get_version().await?` returns the exact build the API host serves
(`system.v1.SystemService/GetVersion`): `version`, the full source revision
`commit`, and the `environment` that answered (`"devnet"`, `"testnet"`,
`"mainnet"` or `"local"`, kept as a string). It needs no API key. A release
reads `"0.10.0"`; a build made after one reads `"0.10.0-12-g4e21a2f09670"`,
which is not a semantic version, so compare `release()` (the part before the

## Triggers

`triggers.list_with(ListTriggersOpts { status: ... })` filters by lifecycle
status. `trigger_type: Some(CreateTriggerType::Ladder)` lists only one trigger
type, and `parent_order_id: Some(order_id)` only the triggers attached to that
order (base58 or decimal, as order reads spell it; an ID that does not parse
or names order 0 fails locally with `Error::Validation`). Leave the other
fields with `..Default::default()`. Valid status values:

`created`, `armed`, `running`, `completed`, `canceled`, `failed`, `paused`

Unknown values return a validation error (they do not silently return an empty
list). Response `status` uses the same labels, with `canceled` spelled as
trigger events and order statuses spell it.

`orders.get_with(GetOrderOpts { key: OrderKey::OrderId(id), include_attached_risk: true, subaccount_id: None, include_attached_risk_state: false })`
returns policy data on `Order.attached_risk`. `Order` also exposes `post_only`.
Identify orders with `OrderKey::OrderId` or `OrderKey::ClientOrderId` (exclusive oneOf).
Set `include_attached_risk_state: true` to populate each decoded leg's optional
`state` (`status`, `armed_ts_ns`, `terminal_ts_ns`, `trigger_id`, and
`child_order_id`). Public trigger/order IDs use the SDK's normal base58 string
format, and nanosecond timestamps use decimal strings. State-only responses
remain visible even when policy fields were not requested: `RiskLeg.trigger_price`
and `TrailingStop.distance` are then `None`, never fabricated zero values.
Policy-only wrappers without a positive TP/SL trigger price or positive
trailing distance are omitted when they have no meaningful runtime state.
Order writes still require those policy fields and reject `None`.
For writes, `oco=true` requires take-profit plus exactly one stop leg
(`stop_loss` or `trailing_stop`); one-leg OCO policies are rejected locally.

`triggers.list_events` returns the same not-found error as `triggers.get`
for an unreadable trigger. It retries catching-up `UNAVAILABLE` responses
with the same bounded policy and request as trigger reads.

A trailing stop created with an activation price the market has already
reached now ends `FAILED` with reason
`TRIGGER_FAILURE_REASON_TRIGGER_WOULD_TRIGGER_IMMEDIATELY` (244).
`ModifyTrigger` and order modifies that would make it act at once are refused
with `ERROR_CODE_TRIGGER_WOULD_TRIGGER_IMMEDIATELY` (302), leaving the
existing state unchanged. To start trailing from the market, clear the
activation price with a present zero.

When modifying a trigger, omit `activation_price` / `max_slippage_ticks` /
`max_slippage_bps` to preserve the current values. A trigger's child limit
price is fixed at create: cancel the trigger and create a new one to change
it. Send an explicit zero
(`Price::from_ticks(0)` or `Some(0)`) to clear an existing activation price
or maximum-slippage cap. A trailing stop's `max_slippage_bps` (standalone or
attached, buy or sell) takes 1–9999 at create. A buy market child and a buy
TWAP slice take up to 10000; a sell market child and a sell TWAP slice take up
to 9999. A modify takes `max_slippage_bps` from 0 (clear) to 10000, as the
API does: a buy stop-loss or take-profit market child can be changed to 10000,
and the server refuses 10000 for a sell one or a trailing stop
(`ERROR_CODE_MAX_SLIPPAGE_INVALID`). Above 10000 fails locally.

A ladder places limit GTC orders only: create it with
`CreateOrderType::Limit`. `CreateOrderType::Market` on a ladder fails locally
with `Error::Validation` before anything is sent, instead of placing resting
limit orders.
Standalone and attached `trailing_distance_bps` require 1–10000. A buy
trailing stop's `limit_price` must be at least its `activation_price`.

`trailing_distance_ticks` and `TrailingDistance::Ticks` are a price delta in 1e-9
quote-unit ticks, the same scale as every price tick, sent as given. They are not
a count of the pair's tick size. On BTC-USDT, a distance of 50 USDT is
`50 × 1_000_000_000 = 50_000_000_000` ticks and 0.5 USDT is `500_000_000`; a value
of `1` trails by 0.000000001 USDT. Convert a decimal distance with `Price`:

```rust,no_run
use polyester::models::TrailingDistance;
use polyester::types::Price;

let ticks = Price::from_decimal_str("0.5", None)?.as_ticks(); // 500_000_000
let distance = TrailingDistance::Ticks(ticks);
```

Trigger reads decode the distance back to quote units
(`TriggerTrailingDetails::trailing_distance`, a `Price`).

`triggers.modify` and `triggers.resume_with` / `resume_by_id` take an optional
symbol: leave it out to target the trigger's own market. An API key limited to
some markets must name the market. A trailing stop's runtime details expose
`trigger_price`, its current threshold, once it is armed.

A trigger's history records every fire refused while it stayed live as a
`fire_refused` event (also a `list_events` filter). It is not terminal: the
trigger keeps its status, so read the trigger's `status` rather than inferring
it from its last event. `TriggerEvent.fire_refusal_reason` says why, as a
failure reason label: `market_halted` or `pair_post_only` (an attached leg
waits for the next price through its trigger price), `min_notional`,
`min_quantity` or `step_size` (the order would have been below the market's
minimum; it fires again once the position changes), `rate_limited` or
`account_repairing` (it retries shortly), or `self_trade_prevented` (self-trade
prevention expired the attached exit's order against another of the account's
resting orders; the leg stays armed and fires again at the next trade through
its trigger price, or once the blocking order is gone). `fire_price` is the
price it fired at. For `self_trade_prevented`, `child_seq` names the child
order that was placed and expired (`CANCEL_REASON_STP_EXPIRE_TAKER` or
`CANCEL_REASON_STP_EXPIRE_BOTH`); for every other reason `child_seq` is an
attempt that placed no order and `child_order_id` is empty. A refusal
that ends the trigger is still `failed` with `failure_reason`. A ladder whose
levels were all canceled before any filled ends `canceled` with
`user_request`.

`TriggerEvent.event_type` is `fired`, `canceled`, `updated`, `failed`,
`activated` (a trailing stop started tracking), `armed` (an attached
take-profit, stop-loss or trailing stop started protecting its parent's filled
quantity, once) or `fire_refused`. A ladder has no event types of its own: read
its status, `completed`, `canceled` or `failed`. A completed ladder may not
have filled: read its executed quantity and levels.

A trigger change that names a listed pair other than the trigger's own is
refused with `ERROR_CODE_TRIGGER_SYMBOL_MISMATCH` (305). Nothing changed: name
the trigger's own pair or omit the symbol. A pair that is not listed is
`ERROR_CODE_UNKNOWN_SYMBOL`. A balance or other ledger read given a zero or
malformed sub-account ID is refused with the ledger code
`ERROR_CODE_INVALID_SUBACCOUNT_ID` (11), read from `Error::Api`'s `code`.

To stop all automated trading, call `client.stop_all_trading(scope)`. Cancel-all
and the dead-man switch cancel open orders, never triggers: an unfired stop
stays armed, a TWAP keeps running. An attached stop-loss, take-profit or
trailing leg whose working exit order a cancel-all cancels ends, and with
`oco` so do its siblings, so the position loses that protection.
`stop_all_trading` pages through the live
triggers (`created`, `armed`, `running`, `paused`), cancels each, then cancels
all open orders, so an order a trigger places before its cancel is still
canceled. Triggers it could not cancel are listed in `trigger_failures`.

`triggers.get` / `get_by_id` and `triggers.list` / `list_with` read your own
writes: once a create, modify, pause or resume has answered, they return the
trigger as changed. Until the change is readable the server answers
`unavailable` (HTTP 503). These reads retry it and `deadline_exceeded` with the same request: 25 ms,
doubling, at most 500 ms, giving up after about 2 s with the final read error. Read a
trigger back after a change with them; don't fall back to a cached copy.

`ListOpenOrdersOpts.trigger_id` / `ListOrderHistoryOpts.trigger_id` filter
child orders created by a standalone trigger (TWAP/ladder slices).
Trigger-event `fire_price` is `None` for time-scheduled TWAP slice fires
(`fire_price_ticks` is optional on the wire). Terminal `cancel_reason` /
`failure_reason` on `Trigger` and `TriggerEvent` decode the proto
`terminal_reason` oneof (empty when unset; unspecified enum → `""`).
When the exchange halts a market it ends the market's open triggers with
`cancel_reason` `market_halted` and cancels its open orders with
`Order.cancel_reason` `CANCEL_REASON_MARKET_HALTED`. A trigger the halted
market refuses reads `failure_reason` `market_halted` when it ends `failed`,
and `fire_refusal_reason` `market_halted` on a refused fire. A reason this SDK
does not name still decodes as `UNKNOWN_TRIGGER_FAILURE_REASON(<n>)`.

`Trigger.version` is 1 for a trigger's first state and higher for every later
state change. Reads and realtime trigger updates carry the same version for
the same state; list results can briefly lag realtime updates, and a realtime
update can repeat an earlier state after a reconnect. Keep the copy with the
highest version and ignore a copy whose version is not higher than the one you
hold. It is `None` from a server that predates trigger versions.

## Qty / price rules

Public order/trigger write paths take **`Price` / `Quantity` wrappers only**:

| Audience | Constructor |
|---|---|
| Humans / demos | `Price::from_decimal_str` / `Quantity::from_decimal_str` (or `from_decimal`) |
| Bots / MMs | `Price::from_ticks` / `Quantity::from_scaled` |

- **Reject floats** (`f32`/`f64`); they are not accepted on these APIs.
- **Reject bare integers** on public order APIs; use the named constructors.
- **Reject excess fractional digits** on decimal→scaled conversion (no silent floor).
- Price ticks are fixed **1e9** (one tick is 0.000000001 quote units); qty scale comes from pair `base_quantity_scale` (catalog).
- Quote budgets use pair `quote_quantity_scale`; retrieve it with
  `Catalogs::quote_quantity_scale_for_symbol[_id]` and construct an
  `OrderQuote` `Quantity`.

## Balances: funding vs trading

Ledger balances have separate **funding** and **trading** buckets per asset.

- An external deposit can stop in **funding** or continue to **trading**,
  depending on its configured route.
- Spot orders spend **trading** balance.
- Move funds funding → trading in the Polyester UI (**Funding → Unified Trading**)
  or on-chain via the funding wallet.

SDK notes:

- **Funding → trading:** on-chain `TradingGateway.deposit` (not an API-key RPC).
  Either encode calldata or submit a UserOp via `PolyesterSmartAccount` with a
  caller-supplied owner EOA key (SDK derives the Polyester Safe; no UI-exported
  owner key).
- **Funding → external:** on-chain `FundingAccount.withdrawToChain` (same
  `polyester::chain`); quote fees with `quote_zipper_fee` first.
- **Whitelist:** FundingAccount allowlist + GuardRegistry signer encoders under
  `polyester::chain` (`encode_add_allowed_external_destinations`, …).
- **Funding → another user's funding wallet:** on-chain `FundingAccount.UAssetTransfer`
  via wallet/smart-account signing in the Polyester app (not an API-key RPC).
- **Trading → funding:** `client.withdraw.create_to_funding(...)` with a signed
  intent payload.
- **Trading → external destination check:**
  `client.withdraw.validate_destination(chain_id, address).await?` returns
  user-safe `valid` / `code` / `message` / `canonical_destination_address`
  without creating a withdraw (create RPCs remain authoritative). An API key
  needs `READ_WITHDRAW_VALIDATION`; `EXTERNAL_WITHDRAW` alone no longer
  opens it.
- **Smart account wallet:** `client.withdraw.get_wallet_balances(None).await?`
  lists the zTokens the account's smart account wallet holds on Polyester
  Chain, such as the refund of a withdrawal Zipper rejected (the amount less
  the fee Zipper kept), with each balance in 18-decimal units (`amount_e18`)
  and whole units (`amount`). Pass a sub-account ID to read that sub-account's
  wallet. An API key needs `READ_BALANCES`.
- **Trading → trading (another account):** `client.internal_transfers.create(...)`.
  The result's `flow_id` names the transfer's lifecycle flow
  (`client.lifecycle.get_flow`). Looking a transfer up by its request or
  transfer ID is session-only and not wrapped.

```rust,no_run
use alloy_primitives::U256;
use polyester::chain::{
    POLYESTER_DEVNET_ENVIRONMENT, PolyesterSmartAccount, encode_trading_gateway_deposit,
};
use std::time::Duration;

let owner_private_key = "0x...";
let u_asset_id = "0x...";
let account = PolyesterSmartAccount::new(owner_private_key, None, 0, Duration::from_secs(60))?;
let call = encode_trading_gateway_deposit(
    &POLYESTER_DEVNET_ENVIRONMENT.contracts.trading_gateway_address,
    u_asset_id,
    U256::from(10u64).pow(U256::from(18u64)),
)?;
let result = account.send_calls(&[call], true, Duration::from_secs(60)).await?;
```

Realtime queues fail with `Error::QueueOverflow` instead of silently dropping;
managed streams rebuild snapshots after reconnect and expose
`on_reconnect` / `on_snapshot_refresh` hooks. Subscribe methods return only
after the initial websocket handshake succeeds; managed create methods also
wait for the initial snapshot. After connection, use
`recv_result().await` or `set_on_error(...)` so delivery failures cannot look
like a clean end of stream. Reconnects use capped exponential backoff with
per-subscription jitter. Snapshot-recovery buffers also fail closed on overflow.

Pass `default_account_id` (your Profile **Account ID**) on the client for bucket
transfers and other account-scoped ledger operations.

Balance fields are ledger u128 wire decimal strings (18-scale). Print them
directly, or format smaller integers with `polyester::codecs::format_ledger_u64`
when you already have a `u64` quantity.

```rust,no_run
use polyester::proto::ledger::read::v1::GetBalancesRequest;

let balances = client.balances.list(GetBalancesRequest::default()).await?;
for bal in balances.balances {
    println!("{} funding={} trading={}", bal.asset_id, bal.funding, bal.trading);
}
```

A sub-account read can include the sub-account's balances in the same shape:
set `GetSubaccountOpts::include_balances`, and `GetSubaccountResult.balances`
is the balances list (`None` when not asked for). It needs the
`READ_BALANCES` action on the sub-account (its role, its attached policy and,
for an API key, the key's policy), or the read fails with `PermissionDenied`
(`AUTH_SUBACCOUNT_ACCESS_DENIED`). An API key bound to a sub-account reads only
that sub-account, and a root-scoped API key cannot read a sub-account's
balances. When balances cannot be read right now the read fails with the
retryable `AUTH_TEMPORARILY_UNAVAILABLE`.

```rust,no_run
use polyester::services::GetSubaccountOpts;

let view = client
    .sub_accounts
    .get(
        subaccount_id,
        GetSubaccountOpts {
            include_balances: true,
            ..Default::default()
        },
    )
    .await?;
for bal in view.balances.map(|list| list.balances).unwrap_or_default() {
    println!("{} available={}", bal.asset_id, bal.available);
}
```

Each `sub_accounts.subscribe` update carries the caller's `role` on the
sub-account (`Some("VIEWER")`, `Some("TRADER")`, ..., as member roles read)
and `removed`. `removed: true` means the caller lost access, for example after
the owner removed it as a member: drop the sub-account from your list. A
removal carries no role, so `role` is `None`; no role is assumed. A role or
access change keeps `revision` and `updated_at`, so apply each update in the
order it arrives rather than by revision.

## Errors, retries, and withdrawal identity

The SDK never follows an HTTP redirect. ConnectRPC calls, realtime token requests and WebSocket
handshakes go through hyper and tungstenite clients that follow none, so a signed request's API key
ID, timestamp and signature never reach a redirect target. A redirect answer fails the call: a
ConnectRPC call with an `Error::Server` naming the HTTP status. Set `api_url` to the API's own origin.

Classify failures with `Error::is_retryable()` and respect `Error::retry_after()`. For mutations,
`Error::mutation_outcome_unknown()` means the first request may have committed: reconcile state
before retrying and reuse the same logical request identity.

An order create, cancel or modify, or a trigger create or change, that was sent but not confirmed
in time fails with an `Error::Api` code from `errors::order_codes::OUTCOME_UNKNOWN`: every
`orders.v1` error code ending in `_OUTCOME_UNKNOWN` (for example
`ERROR_CODE_ORDER_CREATE_OUTCOME_UNKNOWN` or `ERROR_CODE_TRIGGER_CONTROL_OUTCOME_UNKNOWN`). It may
still apply, so `mutation_outcome_unknown()` is true and `is_retryable()` is false: a blind retry
can place a second order. Read the order or trigger back, and reuse the same idempotency key if you
send it again. `AUTH_TEMPORARILY_UNAVAILABLE` and `ERROR_CODE_ACCOUNT_REPAIRING` are retryable and
changed nothing, so `mutation_outcome_unknown()` is false for them. So is
`order_codes::REQUEST_DEADLINE_EXCEEDED` (`ERROR_CODE_REQUEST_DEADLINE_EXCEEDED`, REST 400
`REQUEST_DEADLINE_EXCEEDED`, ConnectRPC `failed_precondition`), which refuses an order or trigger
write whose receive window ended before it was sent on for admission; sending it again signs it with
a fresh timestamp, and `is_request_deadline_exceeded()` reports it.


The retry flag is always false when the mutation outcome is unknown. This includes
bare Connect `unavailable`, `internal` and `deadline_exceeded`, gateway 502/503
bodies, bare or HTML 429 responses and client timeouts. Read back after an unknown outcome; retry reads explicitly. Automatic
trigger reads, status waits and snapshot refresh use read context and can retry these
failures within their existing budgets. Creates are never automatically resent.

A typed `orders.v1.ErrorDetail` carrying `UNAVAILABLE` proves a known, retryable
orders refusal. A bare REST `UNAVAILABLE` or a Connect message with only that
name does not establish its source: outcome unknown and non-retryable. Specific
refusals such as `FEE_SCHEDULE_UNAVAILABLE`, `POLICY_UNAVAILABLE` and
`RATE_LIMIT_POLICY_UNAVAILABLE` are known and retryable on typed Connect,
code-only Connect messages and recognized REST 503 problems. A REST 502 cannot
establish these refusals. `ACCOUNT_ROUTING_INVALID` means the trigger was not
admitted; contact support if it persists.

`RATE_LIMIT_EXCEEDED`, `PRICE_LEVELS_EXHAUSTED` and retry-later capacity codes
are known, retryable admission refusals; preserve and respect any server delay.
The additional retry-later codes are:

- `CLIENT_ORDER_IDS_EXHAUSTED`
- `CLIENT_ORDER_ID_CAPACITY_REACHED`
- `MARKET_LADDER_LIMIT_EXCEEDED`
- `MARKET_TRIGGER_LIMIT_EXCEEDED`
- `MARKET_TWAP_LIMIT_EXCEEDED`
- `NEW_ACCOUNT_CAPACITY_REACHED`
- `REQUEST_RECEIPTS_EXHAUSTED`
- `RESERVATION_CAPACITY_REACHED`
- `TRIGGER_CAPACITY_REACHED`
- `TRIGGER_CONTROL_SHARE_EXHAUSTED`
- `TWAP_CAPACITY_REACHED`

These behave the same on REST, typed Connect and code-only Connect messages.
The resource codes without retry guidance are `ORDER_SEQUENCE_EXHAUSTED`,
`TRIGGER_FIRE_LIMIT_REACHED`, `QUICKSWAP_CAPACITY_REACHED`,
`ACCOUNT_RESERVATION_LIMIT_REACHED` and `TRIGGER_LIMIT_EXCEEDED`: outcome known,
non-retryable, including message-only responses.

Recognized temporary order admission refusals return `Error::AdmissionUnavailable`,
including their canonical service code and REST problem when present.

A plain REST gateway 504 returns `Error::GatewayTimeout`: `is_retryable()` is
false and `mutation_outcome_unknown()` is true. The classifier has no operation
context. Reads may retry a 504 explicitly; writes read back first. A client order
ID supports reconciliation, not exact replay of a single create. Without one,
read open orders before deciding whether to submit again. The SDK never
automatically resends a create; trigger/status reads and snapshot recovery keep
their own safe read retries.

`OVERLOADED` and `SYSTEM_RATE_LIMITED` are retryable admission refusals on
Connect and REST, with no unknown mutation outcome. Respect `retry_after()`
when supplied. Match `Error::RateLimit { code: Some(code), .. }`: `ERROR_CODE_OVERLOADED`
means wait for an outstanding request to complete; `ERROR_CODE_SYSTEM_RATE_LIMITED`
names a venue-wide limit.
`ORDER_SEQUENCE_EXHAUSTED` is permanent; contact support instead of retrying.

The API gateway checks an API-key request's signature and timestamp before any service sees it.
`Error::TimestampSkew` (`TIMESTAMP_SKEW`) means the request timestamp was outside the allowed skew
window. It is retryable: the request did nothing, and a retry signs it again with a fresh
timestamp. If it persists, fix the local clock. Other gateway rejections (`SIGNATURE_INVALID`,
`KEY_DISABLED`, `IP_NOT_ALLOWED`, ...) are `Error::ApiKeyRejected { status, code }` and are not
retryable. `Error::auth_error_code()` returns the code of either.

A REST HTTP 403 problem that refuses the operation rather than the key, such as
`SUBACCOUNT_READ_FORBIDDEN` or `QUICKSWAP_NOT_PERMITTED`, is
`Error::PermissionDenied { code, message, endpoint, .. }`: the key works, but its
account, sub-account role or policy does not allow this call. It is not retryable.

Services answer the same reasons with a ConnectRPC `unauthenticated` error and an
`auth.v1.AuthErrorDetail` (`AUTH_SIGNATURE_INVALID`, `AUTH_TIMESTAMP_SKEW`,
`AUTH_MISSING_HEADERS`, `AUTH_KEY_EXPIRED`, `AUTH_KEY_DISABLED`,
`AUTH_IP_NOT_ALLOWED`, `AUTH_API_KEY_NOT_ACCEPTED`, `AUTH_RECV_WINDOW_INVALID`); they map to the
same `Error::TimestampSkew` and `Error::ApiKeyRejected`. `Error::is_recv_window_invalid()` reports
`AUTH_RECV_WINDOW_INVALID` (REST 401 `RECV_WINDOW_INVALID`), an `X-API-RECV-WINDOW` header that is
not one whole number from 1 to 60000; fix `Config::recv_window_ms`. `Error::auth_code()`
returns the typed `auth.v1.AuthErrorCode` whichever transport answered: the
Connect detail, or a REST problem or gateway `code` with `AUTH_` added
(`UNAUTHENTICATED` reads `AUTH_AUTHENTICATION_REQUIRED`). Only
`AUTH_TIMESTAMP_SKEW` is retryable among these. `auth_codes::REPLAY_CAPACITY_EXHAUSTED`
(`AUTH_REPLAY_CAPACITY_EXHAUSTED`, REST 429 `REPLAY_CAPACITY_EXHAUSTED`, ConnectRPC
`resource_exhausted`) is not a credentials refusal: the server remembers every signed request until
its receive window ends, so it cannot be replayed, and the key or its account holds its full share
of that record. The request was not processed and the share frees as earlier windows end, so it is
an `Error::RateLimit` with that code, and `is_retryable()` and `is_replay_capacity_exhausted()` are
true. It carries no `Retry-After`: back off briefly and send again, which signs again. A shorter
`Config::recv_window_ms` makes room sooner. `auth_codes::WALLET_ALREADY_LINKED`
(`AUTH_WALLET_ALREADY_LINKED`, ConnectRPC `already_exists`, REST 409) refuses a
wallet login whose wallet is already linked to another account; it is a
terminal `Error::Api`, and `Error::is_wallet_already_linked()` reports it. Log
in with the account address the wallet already uses.

```rust,no_run
use polyester::proto::auth::v1::AuthErrorCode;

match client.orders.list_open(None).await {
    Err(err) if err.auth_code() == Some(AuthErrorCode::AUTH_IP_NOT_ALLOWED) => {
        eprintln!("call from an address on the key's allowlist");
    }
    other => { other?; }
}
```

Session-only methods (a wallet trading withdraw, the auto-withdraw rule writes,
the portfolio equity reads, ...) refuse an account API key with
`AUTH_SESSION_KIND_NOT_ALLOWED`, HTTP 403. It maps to one error,
`Error::SessionRequired`, on ConnectRPC and REST alike
(`Error::is_session_required()`); call the method with a session token. An API
key whose policy lacks an action gets `permission_denied` with a message that
names it, such as `api key policy does not allow READ_AUTO_WITHDRAW`; the
message reaches you as is.

Order refusals name the request fields to fix: `Error::violations()` lists the
`orders.v1.ErrorDetail` violations (`field_path`, `rule_id`, `message`) with
ConnectRPC field paths, such as `order.base_qty_scaled` for an off-step
quantity or `order.limit_gtc.price_ticks` for an off-tick price. Branch on the
code, then on `rule_id`.

A cancel of an order that has already ended, a repeat of the cancel that ended
it included, is refused with `ERROR_CODE_ORDER_ALREADY_TERMINAL`:
`Error::is_order_already_terminal()` is true. Treat it as "already done" and
read the order for how it ended. Retry a cancel by order ID once you have it: a
client order ID names its order for at least a minute after the order ends,
then reads `ERROR_CODE_ORDER_UNKNOWN`. Every cancel counts against the cancel
rate limit, repeats included.

A sub-account member call that targets the sub-account's owner (inviting the owner, accepting
an invite for the owner, changing the owner's role or removing the owner) is refused with
`AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED`: ConnectRPC `failed_precondition`, REST HTTP 412. Both map to
`Error::Api` with that code; `Error::is_subaccount_owner_role_locked()` is true for it, and it is
not retryable. Show "The owner's role can't be changed", and don't offer role changes, removal or
invites for the member whose role is `OWNER`.

`Error::NotImplemented` means the server does not offer the call (Connect `unimplemented`, or a
contract code at HTTP 501); `Error::RouteNotFound` is the narrower bare HTTP 404.
`Error::is_not_implemented()` is true for both, and neither is retryable.

An HTTP error with no code the contract defines can come from a gateway or an edge, so it doesn't
prove a request was refused. Only a 401 or 403 is a refusal on its status alone (`Error::Auth` or
`Error::ApiKeyRejected`). Every other status returns `Error::Server` with
`mutation_outcome_unknown()` true and `is_retryable()` false, and names any code it did send in its
message; read back before sending a mutation again. Trigger reads retry 429, 502, 503 and 504 for you; retry other reads yourself if you want to. A
bare 404 stays `Error::RouteNotFound`, also with an unknown outcome. A well-formed but unrecognised
code at HTTP 429 returns `Error::Api`: known and not retryable.

A `cancel_all_with` retry with the same `request_id` within 120 seconds returns the original
counts with an empty `cancelled_orders` and `listing_status` `not_retained_read_open_orders`.
An empty retried list does not mean nothing was canceled: read open orders for current state.

Connect `ResourceExhausted` maps to `Error::RateLimit { detail, .. }`. When the server attaches
`polyester.ratelimit.v1.RateLimitDetail` (top-level Connect detail or nested under
`orders.v1.ErrorDetail.rate_limit`), `detail` carries `policy_class`, `scope`, `operation_id`, and
presence-aware quota fields. A REST `RATE_LIMIT_EXCEEDED` problem is the same `Error::RateLimit`,
whichever side refused, with its `rate_limit` object in `detail`; every field is optional. The
gateway's own refusal names only `reason` and `scope` (`CLIENT_IP`, no `operation_id`); a
service's also names the operation, the policy class and the remaining quota. The gateway's
Connect refusal (`resource_exhausted`, "rate limit exceeded, retry later") has no detail at all.
`retry_after` prefers `detail.retry_after_ms`, then `Retry-After` / `Retry-After-Ms` /
`grpc-retry-pushback-ms` headers, and is `None` when the server gave no hint, as for a refusal
of too many concurrent requests: back off on your own schedule then. A 429 problem with another
code, such as `AUTH_RESOURCE_EXHAUSTED` (no new account can be created), is an `Error::Api` that
waiting does not resolve.

A request body over an endpoint's size limit is refused with HTTP 413 and the problem
`REQUEST_TOO_LARGE` on every service, before the request is authenticated. It is an `Error::Api`
with code `problem_codes::REQUEST_TOO_LARGE` and the problem in `http_problem()`;
`Error::is_request_too_large()` reports it. Nothing changed and the same body is refused again:
reduce it to fit the limit. A ConnectRPC message over the limit once decoded keeps its Connect
`resource_exhausted` answer and maps as before.

Preview and batch rejections expose the same
payload on `OrderErrorDetail.rate_limit` / batch item `rate_limit`. That error payload is
distinct from `client.rate_limits` (`ratelimit.v1.RateLimitService`), which returns the
public trading quota catalog and authenticated account / API-key limits.

Order mutations that take a `request_id` (`modify`, `batch_create`, `batch_cancel`,
`batch_replace`, `cancel_all` / `cancel_all_with`, `cancel_all_after`) **generate one when
omitted**, matching TypeScript/Go/Python. That is fine for one-shot calls. **Do not blind-retry
after an ambiguous failure while omitting `request_id`**: each omitted call mints a *new* id, so
the retry is a second logical mutation rather than an idempotent replay. Generate or choose a
stable `request_id` once, persist it with the attempt, and pass the same value on retry (same
rule as `client_order_id` on create). Convenience helpers that do not accept `request_id`
(for example `cancel_all`) are one-shot oriented - use the `*_with` / explicit-argument form when
you need retry-safe identity.

Batch replace returns admission, not execution finality. Each item amends its
order in place, under the same order ID and with its queue priority kept, when
it keeps the price, does not raise the total quantity and keeps the client
order ID. A new price, a larger total quantity or a new client order ID
replaces the order with a successor under a new order ID, with its queue
priority reset. A new total quantity at or below the filled quantity ends the
order at its filled quantity, with no successor. Each admission and status
item carries `action_taken`: `replaced` when a successor took over, or
`amended` when the order kept `old_order_id`.

An admitted item can still be refused when it is applied, for example a
post-only order moved to a price that would cross. The admission's planned
`replacement_order_id` is therefore not proof of an order: only the batch
status or order reads confirm one. Reuse the same `request_id` when retrying a
logical batch, then call `orders.wait_batch_replace(batch_request_id, None,
None)`. It polls `get_batch_replace_status` with a short backoff until no item
is `admitted` (each is `working`, `rejected` or `terminal`) and returns that
status. `working` is live, not terminal execution. The status is retained for
60 seconds from acceptance and is readable as soon as `batch_replace` returns.
`get_batch_replace_status` returns the retryable `Error::AdmissionUnavailable`
for `unavailable` (send the same read again within the window), and
`not_found` means no retained batch with that ID, never a rejected
replacement. The helper polls through `unavailable`, and through `not_found`
because an older API could answer it for a few seconds after admission. After
the window, reconcile the individual orders with `orders.get` and never send
an accepted batch again. An item's `updated_ts_ns` is an observation time, not
the refusal's identity. A
refused item reads `rejected` with `code`, the refusal without its
`ERROR_CODE_` prefix (`POST_ONLY_CROSS`); `item.error_code()` gives the full
code an `Error::Api` from a single modify carries (`ERROR_CODE_POST_ONLY_CROSS`),
and keeps a code this SDK does not know unchanged. The order keeps its previous
price and quantity under `old_order_id`, and the item has no
`replacement_order_id`. The server keeps a batch's status for 60 seconds: the
helper stops at the end of that window (or an earlier `timeout`) with
`Error::Transport`, because after it the status proves nothing; reconcile
through the orders themselves.

```rust,no_run
use polyester::models::{CreateOrderParams, ModifyOrderParams};
use polyester::{Client, Result};

async fn create_with_reconciliation(client: &Client, params: CreateOrderParams) -> Result<()> {
    match client.orders.create(params.clone()).await {
        Ok(order) => println!("{}", order.order_id),
        Err(error) if error.mutation_outcome_unknown() => {
            // The order may have been admitted. Look up params.client_order_id
            // (get / list_open) before creating again with the same client_order_id.
            // A second create with the same id is rejected if the first attempt admitted.
        }
        Err(error) if error.is_retryable() => {
            if let Some(seconds) = error.retry_after() {
                tokio::time::sleep(std::time::Duration::from_secs_f64(seconds)).await;
            }
            // Nothing was applied; create again with the same client_order_id.
        }
        Err(error) => return Err(error),
    }
    Ok(())
}

async fn modify_with_stable_request_id(client: &Client, mut params: ModifyOrderParams) -> Result<()> {
    // Choose once per logical modify; reuse on every retry of that attempt.
    params.request_id = Some("mod-bot-attempt-42".into());
    let _ = client.orders.modify(params).await?;
    Ok(())
}
```

Trading withdrawals require a caller-owned non-empty idempotency key and non-zero nonce. Generate
each once per logical withdrawal, persist both with the signed payload, and reuse the entire
request after an ambiguous timeout:


## Public market data

Public endpoints do not require an API key. Authenticated endpoints use the
credentials above.

```rust,no_run
let candles = client
    .market_data
    .get_candles("BTC-USDT", "1m", Some(50))
    .await?;
let current: Option<_> = client
    .market_data
    .get_current_candle("BTC-USDT", "1m")
    .await?;
let trades = client.market_data.get_trades("BTC-USDT", Some(20)).await?;
// Gap-free backfill: walk trades by trade ID from a cursor (0 = the first
// trade), then continue from `next_after_trade_id`. When it does not move,
// nothing newer is available yet.
let backfill = client
    .market_data
    .get_trades_with(polyester::models::GetTradesOpts {
        symbol: Some("BTC-USDT".into()),
        after_trade_id: Some(0),
        limit: Some(500),
        ..Default::default()
    })
    .await?;
let _next_cursor = backfill.next_after_trade_id;
let _ = (candles, current, trades);

client.wait_for_catalogs().await?;
let mut sub = client.market_data.subscribe_trades("BTC-USDT").await?;
sub.set_on_error(|error| eprintln!("realtime interruption: {error}"));
if let Some(trade) = sub.recv_result().await? {
    println!(
        "{:?} {:?}",
        trade.price.as_ref().map(|p| p.as_ticks()),
        trade.qty.as_ref().map(|q| q.as_scaled())
    );
}
```

`orderbook.get` returns `OrderbookData`. Its `available` is true when the
book is current, so an empty side means no liquidity. When it is false the
book is being built or was invalidated: its levels are unknown, not empty, so
fetch it again later instead of reading empty sides as no liquidity. It is the
server's value as sent, never inferred from the levels; a managed order book
subscription carries the value of its last snapshot. A server that predates
the field reports false.

`get_candles` and `get_candles_with` return rows newest-first by `ts_sec`.
When incomplete rows are included, the current open candle is prepended.

## Realtime

Realtime is binary-only. Account orders stream over the private WebSocket;
every other stream uses Centrifugo channels.

Centrifugo streams negotiate the `centrifuge-protobuf` WebSocket subprotocol,
send binary length-delimited Centrifugo commands, and decode protobuf
publication payloads from `:proto` channels. ConnectRPC's optional JSON wire
mode does not apply to realtime. Incoming WebSocket messages, frames, and
protobuf record lengths are capped at 8 MiB.

Public trade, user fill, ledger transfer and trigger-event publications are
batches. Their subscriptions yield every event in order, one at a time; an
event that fails to decode is reported through `set_on_error` and the rest of
its batch is still delivered. Both legs of a ledger transfer share
`LedgerTransfer.transfer_id`. `LedgerTransfer.balance_after` is the account
bucket's balance after the transfer, an exact integer at the 18-decimal ledger
scale like `amount`, or `None` when the server sends none.
`LedgerTransfer.link_id` is the decimal correlation ID of related legs, `None`
when there is none. Use `realtime::Client::subscribe_proto_batch`
for a batched channel of your own.

A market overview subscription created with `symbols` keeps only those
markets, in its snapshot and in every update.

Realtime subscription handles stop their background tasks when explicitly
closed or dropped. Call `close()` when prompt shutdown matters; `Drop` provides
the cleanup safety net.

### Order stream

`orders.subscribe` streams an account's live orders over the private WebSocket
(`/v1/ws/private` on the API host, subprotocol `polyester.v1.proto`). It
authenticates with the same signed realtime tokens as the other private
streams. Events arrive as `PrivateOrdersEvent`:

| Event | Meaning |
| --- | --- |
| `Connected` | The server confirmed the subscription; again after each reconnect |
| `Snapshot(orders)` | The account's full live view; replace local state with it |
| `Unit(unit)` | One change: changed orders (complete), removed order IDs, and events (fills, cancels, rejections, command outcomes) |
| `Ready` | The stream reached the account's read boundary: it reflects every acknowledgement and order read made before the subscription. Once per server subscription, so again after a reconnect |
| `Stale(stale)` | `stale.stale` true: the view is temporarily not current, with a `reason` such as `view_behind`. For `order_unavailable` only the orders in `order_ids` are not current; the rest of the view is, and units keep arriving. A later report replaces the earlier one. `stale.stale` false: all of the view is current again |
| `Disconnected` | The stream dropped; it resumes by itself unless an error ended it |
| `Error(error)` | A stream error; a terminal one is followed by `Disconnected` and the end of the stream |

Orders use the same `Order` model as the order reads. Keep the copy with the
higher `version`; equal versions are identical. Wait for `Ready` before
relying on the stream: to combine it with an order read, read first, then
subscribe, wait for `Ready`, and merge both by `version`. The stream reconnects with
backoff, resumes from its last applied position, and takes a fresh snapshot
when it cannot resume. If the server does not confirm a subscribe within 30 s, a
new subscription ends with `Error::RealtimeSetupTimeout`; a confirmed one reports it
as `Error(error)` and subscribes again with backoff. Several `orders.subscribe` calls for one account share
one server subscription.

```rust,no_run
use polyester::models::{OrderUnitEvent, PrivateOrdersEvent};
use polyester::services::CreateSubscriptionOptions;

let mut orders = client.orders.subscribe(None).await?;
while let Some(event) = orders.recv_result().await? {
    match event {
        PrivateOrdersEvent::Snapshot(live) => println!("{} live orders", live.len()),
        PrivateOrdersEvent::Ready => println!("order stream is current"),
        PrivateOrdersEvent::Unit(unit) => {
            for order in unit.orders {
                println!("{} {} v{}", order.order_id, order.status, order.version);
            }
            for event in unit.events {
                if let OrderUnitEvent::Order(event) = event {
                    // `rejected`: reject_reason; `canceled`, and the `replaced`
                    // event of the order a replace ended: cancel_reason.
                    println!("{} {:?} {:?}", event.kind, event.reject_reason, event.cancel_reason);
                }
            }
        }
        PrivateOrdersEvent::Error(error) => eprintln!("order stream: {error}"),
        _ => {}
    }
}

let mut api_policies = client.policies.subscribe_api_policies(None).await?;
if let Some(policy) = api_policies.recv_result().await? {
    // `actions` are `auth.v1.PolicyAction` names, such as "READ_SPOT" or "READ_API_KEYS".
    println!("{} {} {:?}", policy.policy_id, policy.revision, policy.actions);
}


let mut book = client
    .orderbook
    .create_subscription(CreateSubscriptionOptions {
        symbol: "BTC-USDT".into(),
        depth: Some(50),
        ..Default::default()
    })
    .await?;
book.set_on_error(|error| eprintln!("managed order book failed: {error}"));
if let Some(snapshot) = book.updates().recv().await {
    println!("{} {}", snapshot.book_seq, snapshot.bids.len());
}
```

`orderbook.get` takes the snapshot depths 1, 5, 10, 20, 50, 100, 200, 500 and 1000.
Any other depth up to 1000 requests the smallest of them that covers it, 20 for
`Some(11)`, and `None` or `Some(0)` means 50; the result's `depth` is the depth
requested (`polyester::codecs::decode::orderbook_snapshot_depth`). A depth above
1000 is an `Error::Validation` before any request.
The delta stream is published at fewer depths, 1, 20, 50, 200 and 500
(`polyester::codecs::decode::ORDERBOOK_STREAM_DEPTHS`), and the server accepts a
subscribe at any other depth and then sends nothing on it, so the SDK does not
subscribe there:

- `orderbook.create_subscription` with `depth: Some(10)` takes any depth from 1 to
  500. It rides the smallest published depth that covers it, 20 here, with its
  snapshot, and trims each view to 10 levels. Its update rate is that of the depth it
  rides, and each published update adds a view, also when only levels outside yours
  changed. With `bucket`, levels are aggregated first and the depth then counts
  buckets. A depth above 500, or `Some(0)`, is `Error::Validation` before connecting;
  for more than 500 levels, read a snapshot with `orderbook.get`.
- `orderbook.subscribe_deltas` delivers raw deltas, which can't be trimmed, so it takes
  only a published depth and returns `Error::Validation` for any other.

A snapshot applied with the publications buffered behind it adds one view, at the
last buffered sequence.

A stream that stops and a market with nothing to report look alike, since no view
arrives in either case. `since_last_publication()` on a managed order book tells them
apart: the time since its stream last delivered a publication (or since the
subscription started); views from a snapshot or a bucket change don't count. The
server republishes each book's whole view about every 30 s even when nothing changed
(seen on every market of devnet and testnet; the public contract does not promise a
cadence), so a quiet market stays under that. The SDK sets no threshold and acts on
none. Poll it, and treat an age far above 30 s, such as 90 s, as a stall: call
`refresh_snapshot()`, or close and subscribe again.

```rust,no_run
if book.since_last_publication() > std::time::Duration::from_secs(90) {
    book.refresh_snapshot().await?;
}
```

Streamed orders carry scaled quantity integers but may not carry the
base quantity scale, so `Quantity::scale()` can return `None`. A bot must
resolve the scale from the hydrated catalog using `Quantity::symbol_id()` (or
`Quantity::symbol()`), then pass that catalog scale to `Quantity::format`.
Never trust, guess, or invent a stream quantity scale.


### Subscriptions the server ends

When the server ends a realtime subscription, the receiver delivers what is
queued and finishes, and `err()`, `recv_result()` and the error callback report
`Error::SubscriptionEnded` with the channel, the server's code and text, and
`reason`. Managed order books and market overviews finish `updates()` and report
the same error.

The exception is a sub-account's balances, transfers, trades, triggers or
lifecycle channel: the server can end one of those after access was granted
again, so the SDK reads `ListSubaccounts` and, while the sub-account is listed
with a role, subscribes again with a fresh token. `take_resubscribed()` reports
the gap. It stops, with the reason, when a `removed` update for that sub-account
arrived on this client, when the list no longer has it, when the list or the
token is refused (`cause` holds the refusal), or after 6 attempts that did not
stay up for a minute. Requests are paced across the client, so many subscriptions
ending together share one list read per second and at most five attempts per
second. An API key bound to a sub-account sees that sub-account in the list; a
root key cannot subscribe to a sub-account's channels.

Setting up a subscription has one deadline, 30 seconds or twice the configured
HTTP timeout if longer, covering the connection, both tokens and both
confirmations. A server that keeps the connection alive without confirming fails
with `Error::RealtimeSetupTimeout`.

A managed order book requests an unavailable snapshot again by itself, after 1 s
doubling to 8 s, until the book is available or the subscription stops; repeated
unavailable answers add no view. A market whose book stays unavailable keeps being
requested once every 8 s, so a bot recovers by itself when the book comes back;
close the subscription to stop.

## Auth signing

Authenticated Connect calls sign the **exact configured wire body bytes**
(protobuf or JSON) with:

```text
timestamp_ms
METHOD
pathname
canonical_query
hex(sha256(body))
```

Headers: `X-API-KEY-ID`, `X-API-TIMESTAMP`, `X-API-SIGNATURE`.

Use the high-level `Client` service methods for authenticated calls. Generated
clients under `polyester::connect` are low-level protocol bindings and do not
apply Polyester API-key signatures by themselves.

## Lifecycle flow lists

A flow list that selects an account (`owner_account_id` or `smart_account_address`) returns the
flows it owns and the transfers other accounts sent to it, such as a transfer from another user or
sub-account, or a reward payout. Each row's `participation` says which: `owner` (its deposit,
withdrawal, or a transfer it sent, including a move between its own Funding and Trading balances)
or `recipient`. For a transfer, the counterparty is `destination_address` when the account sent it
and `source_address` (with `owner_account_id`) when it received it. `ListFlowsRequest::participation`
narrows the list to one side; the server refuses it without an account.

```rust,ignore
use polyester::proto::chain::lifecycle::v1::__buffa::oneof::list_flows_request::AccountSelector;
use polyester::proto::chain::lifecycle::v1::{FlowParticipation, ListFlowsRequest};

let page = client
    .lifecycle
    .list_flows(ListFlowsRequest {
        account_selector: Some(AccountSelector::OwnerAccountId(account_id)),
        participation: FlowParticipation::PARTICIPATION_RECIPIENT.into(),
        limit: 20,
        ..Default::default()
    })
    .await?;
```

A page token is bound to the request it was returned for: continue with the same account,
participation, scope and order; only `limit` may change.

## Lifecycle transaction lookups

One chain transaction can reference multiple lifecycle flows when operations
are bundled. Transaction lookups therefore return a page, not one flow:

```rust
let mut request = ListFlowsByTxRequest {
    tx_hash: tx_hash.to_owned(),
    lookup_kind: TxLookupKind::TX_ANY.into(),
    limit: 50,
    ..Default::default()
};
let mut flow_ids = Vec::new();
loop {
    let page = client.list_flows_by_tx(request.clone()).await?;
    flow_ids.extend(page.flows.into_iter().map(|flow| flow.intent_id));
    if page.next_page_token.is_empty() {
        break;
    }
    request.page_token = page.next_page_token;
}
```

`Client::get_flow_by_tx` also returns the complete requested page. Use
`Client::list_flows_by_tx` when following pagination.
